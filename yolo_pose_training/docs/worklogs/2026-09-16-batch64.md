# 2026-09-16 batch 64 與顯存降級

## 變更與原因

使用者修正訓練 batch：優先 64，顯存不足則 32 或 16。四階段 YAML、重建腳本及背景佇列均同步更新。最終獨立 val 比較 batch 保留 8，與訓練分開。

停止本任務既有程序並保留所有 checkpoint，Stage 1 從完成第 8 個 epoch 的 last-resumable.pt 接續，先嘗試 64；已完成的 8 輪使用 batch 16，不改寫歷史。中斷時尚未完成的部分 epoch 由 checkpoint 重做。

官方 OOM 原地恢復會重建 optimizer，且可能降至 8；因此停用原地恢復，改由父程序捕捉專用退出碼 42，以新程序依 64、32、16 接續。每次重試優先載入本階段完整 checkpoint；尚未產生 checkpoint 時從階段初始權重重試。16 仍不足就停止，不無限重試。新 tmux session 為 bbat5_pose_20260916_batch64，仍每 600 秒記錄 GPU，每 5 秒檢查退出。

## 驗證方式與結果

Python 語法檢查通過；四階段 YAML 經官方 get_cfg 驗證 batch=64。讀取既有 checkpoint 確認已完成 8 輪且 optimizer 狀態存在。實際訓練啟動確認見下方追加結果。

## 困難與解法

既有訓練程序不會動態讀取 YAML，故只停止本任務程序後以 checkpoint 接續。官方 OOM fallback 可能丟失 optimizer 動量且低於使用者下限，改由背景佇列在新程序中降級。其他困難：無。

## 未解事項與風險

尚未跑到全部解凍或 960 階段，實際 batch 需由各階段顯存需求決定。既有前 8 輪 batch 16 與後續新 batch 不同；維持原始 seed 與 LR，但接續不保證與不中斷训练逐步一致。最終比較尚未完成。
